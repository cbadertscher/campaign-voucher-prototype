# Campaign-Voucher System — Prototype Specification

**Goal:** a faithful, end-to-end prototype whose gas costs are measured on a real run —
real ZK credential verification at account creation, the real ERC-4337 sponsored path,
and a final fiat cost estimate on **L1 and Base (L2)**. No mocks on the critical path.
This specification is written to be precise enough to hand directly to Claude Code to
drive the implementation.

---

## 0. Definitions

- **Citizen** — a real person holding a national eID; on-chain, one pseudonymous
  ERC-4337 account, unlinkable to the eID.
- **Authority** — issues the eID-backed credential off-chain; on-chain presence is one
  published public key.
- **Candidate / Vendor** — public, KYC'd entities on admin-approved allowlists.
- **Sponsor** — pays gas via an ERC-4337 paymaster; trustless.
- **Voucher** — one discrete ERC-721 token; the unit of campaign-finance value.

---

## 1. Locked decisions

1. Vouchers are **discrete ERC-721** tokens (one token = one voucher, always live).
2. **ZK runs exactly once, at account creation.** The credential is presented to the
   factory; the resulting account is a persisted "accredited citizen." Everything after
   — claim, donate, spend, redeem — is authorized by the account's owner signature, with
   **no proof and no further nullifier.**
3. **No citizen→citizen transfer** in this prototype.
4. **Batching only** on the two accumulation outflows (candidate→vendor, vendor→authority).
5. **One voucher per credential** in this prototype, enforced compositionally: one account per credential
   (nullifier consumed at creation) ∘ one voucher per account (`hasClaimed` flag). The
   voucher is obtained by a **separate claim call** the accredited account makes; the
   claim carries no credential material.
6. **Account authorization:** simple ECDSA owner key (`ecrecover(userOpHash) == owner`).
7. **ERC-4337 EntryPoint v0.7** (`eth-infinitism/account-abstraction`).
8b. **One deployment per election.** Factory, citizen allowlist, voucher contract, and
   paymaster are deployed per election; the nullifier is scoped by `electionId`, so one
   credential serves every election but yields one account per election.
8. **Proving system:** Groth16 over BN254; Poseidon hashes; EdDSA-BabyJubjub for the
   authority signature (all circomlib). Generated `Verifier.sol`.
9. Cost reported for **L1 and Base**.

---

## 2. Architecture

| Component | Kind | Responsibility |
|---|---|---|
| `AllowList` ×3 | contract | citizen / candidate / vendor membership |
| `CredentialVerifier` | contract | generated Groth16 verifier (`verifyProof`) |
| `CitizenFactory` | contract | verify proof, consume nullifier, deploy account, register citizen (**the only ZK site**) |
| `CitizenAccount` | contract | ERC-4337 account; ECDSA `validateUserOp` + `execute` |
| `VoucherNFT` | contract | ERC-721 vouchers; transfer-rule state machine; one-per-account claim; outflow batching |
| `VoucherPaymaster` | contract | ERC-4337 paymaster; sponsors approved ops |
| EntryPoint v0.7 | external | canonical singleton; not written by us |

Trust anchor: the authority's public key and the ZK verification key are compiled
immutably into `CitizenFactory`. `VoucherNFT` holds **no verifier** — it trusts only the
citizen allowlist (accreditation) plus its own claim flag. Off-chain trust enters the
system at exactly one on-chain point: the factory's proof check.

## 3. Component specifications

### 3.1 `AllowList`
```solidity
address public admin;                          // citizens: the factory; others: authority
mapping(address => bool) public isRegistered;
function register(address who) external onlyAdmin;
function revoke(address who) external onlyAdmin;
```

### 3.2 `CredentialVerifier` + circuit
Generated by snarkjs from the Circom circuit. Statement:

- **Public signals:** `authorityPubKey` (or embedded constant), `nullifier`, `owner`,
  `electionId`.
- **Private inputs:** secret `s`, commitment `C`, signature `(R8, S)`.
- **Constraints:**
  1. `C == Poseidon(0, s)`   (commitment; domain tag 0)
  2. EdDSA-Poseidon: `(R8,S)` is a valid `authorityPubKey` signature on `C`
  3. `nullifier == Poseidon(1, s, electionId)`   (domain tag 1, **scoped per election**)
  4. `owner` bound as a public signal (stops proof re-use under another owner)
  5. `electionId` bound as a public signal (ties the proof to one election)

**Election scoping.** The authority's signed commitment `C = Poseidon(0, s)` is
election-independent — one credential per citizen, reusable across elections. Only the
*nullifier* is scoped: `Poseidon(1, s, electionId)` yields a **different, mutually
unlinkable** nullifier per election, so a citizen gets one account per election, and
accounts for different elections cannot be correlated. `owner` may also differ per
election (a citizen may use a fresh key each time).

Deliver `circuits/credential.circom`, a Powers-of-Tau + circuit-specific setup script,
`Verifier.sol`, and a fixture generator producing `(proof, pubSignals)` for tests.

### 3.3 `CitizenFactory` (the single ZK site) — one instance per election
```solidity
IVerifier immutable verifier;  AllowList immutable citizens;  // citizens.admin == this
uint256   immutable electionId;                               // fixed at deployment
mapping(bytes32 => bool) public nullifierSpent;
function createAccount(bytes calldata proof, uint256[] calldata pubSignals) external returns (address);
```
**One factory (and one citizen `AllowList`, `VoucherNFT`, paymaster) is deployed per
election.** `electionId` is an immutable constant of the deployment — there is no
election registry and no cross-election state.

Order: (1) parse `nullifier`, `owner`, `electionId'` from `pubSignals`;
(2) `require(electionId' == electionId)` — the proof must be for *this* election;
(3) `require(!nullifierSpent[nullifier])`; (4) `require(verifier.verifyProof(proof, pubSignals))`;
(5) set `nullifierSpent`; (6) `CREATE2` deploy `CitizenAccount(owner)` with
`salt = keccak256(nullifier, owner)`; (7) `citizens.register(account)`.
**Faithful path:** creation via EntryPoint `initCode` (counterfactual, sponsored). Because
the factory writes shared storage during 4337 validation, it **MUST be a staked entity**
(ERC-7562); document the stake in the deploy script.

### 3.4 `CitizenAccount` (ERC-4337 v0.7)
```solidity
constructor(address owner);                             // owner written to mutable storage
function validateUserOp(PackedUserOperation calldata op, bytes32 opHash, uint256 missing)
    external returns (uint256 validationData);          // ecrecover(opHash) == owner
function execute(address to, uint256 value, bytes calldata data) external; // onlyEntryPoint
function rotateOwner(address newOwner) external;        // onlyEntryPoint (self-call)
```
**How the owner key takes control (no separate "submit key" step).** The user generates
an ECDSA keypair off-chain and places its *address* into the proof's `owner` public
signal (constraint 4). `createAccount` passes that `owner` to the constructor, which
stores it. Thereafter `validateUserOp` authorizes ops by `ecrecover(opHash) == owner`.
Only the **address** ever appears on-chain or in the proof — never the private key.
Because `owner` is a bound public signal, a relayer/sponsor cannot substitute their own
key: changing `owner` invalidates the proof.

**Immutable address, mutable key.** `owner` is baked into the CREATE2 salt
(`keccak256(nullifier, owner)`), so the *initial* owner fixes the address; but it is
stored in **mutable storage**, so `rotateOwner` can change the controlling key later
(loss/rotation) without moving the address. Do not bake `owner` into immutable code.
Signature check isolated in one internal `_validateSignature` for a later passkey swap.

### 3.5 `VoucherNFT` (ERC-721, OZ v5) — no verifier, no nullifier
```solidity
address   immutable authority;
AllowList immutable citizens, candidates, vendors;
mapping(address => bool) public hasClaimed;   // one voucher per accredited account
uint256   public nextId;

function claimVoucher() external;                                   // accredited citizen; mints 1 to msg.sender
function batchTransfer(address to, uint256[] calldata ids) external;// candidate -> vendor (spend)
function redeem(uint256[] calldata ids) external;                   // vendor -> 0 (burn)
function _update(address to, uint256 id, address auth) internal override;
```
`claimVoucher()`: `require(citizens.isRegistered(msg.sender))`, `require(!hasClaimed[msg.sender])`,
set the flag, `_mint(msg.sender, nextId++)`. Owner-signed via the account; sponsored. No
proof, no nullifier — accreditation already happened at account creation.

**Transfer-rule state machine (`_update`)** — every other `(from,to)` role pair reverts:

| From | To | Meaning | Extra check |
|---|---|---|---|
| 0 (mint) | citizen | voucher claim | via `claimVoucher`: accredited + `!hasClaimed` |
| citizen | candidate | donation | `to` is a registered candidate |
| candidate | vendor | spend | `to` is a registered vendor |
| vendor | 0 (burn) | redemption | via `redeem`: caller is that vendor |

### 3.6 `VoucherPaymaster` (ERC-4337 v0.7 `BasePaymaster`)
Sponsors gas only for ops whose target is the factory, a registered citizen account, or
`VoucherNFT`; rejects anything else (anti-griefing) and respects ERC-7562 storage rules.
Funded by an authority deposit in the EntryPoint; staked as required. Policy in one
internal function for easy tightening.

## 4. Canonical end-to-end walkthrough (the headline measurement)

One Foundry test, real EntryPoint + paymaster + verifier, no mocks, gas at each step and
total:

1. **Create account** — sponsored userOp with `initCode` → factory verifies a real
   Groth16 proof, consumes the nullifier, deploys the account, registers it. *(only ZK step)*
2. **Claim voucher** — sponsored, owner-signed userOp → `VoucherNFT.claimVoucher()`; mints one.
3. **Donate** — sponsored, owner-signed → account calls `transferFrom(citizen, candidate, id)`.
4. **Spend** — candidate calls `batchTransfer(vendor, ids)` (EOA/multisig; not sponsored).
5. **Redeem** — vendor calls `redeem(ids)`.

Output: per-step gas (incl. EntryPoint + paymaster + validation overhead) and a grand
total for one voucher's full life.

## 5. Invariants (must be tested)

- I1. Vouchers move only 0→citizen→candidate→vendor→0. Any other edge reverts (fuzz role pairs).
- I2. One account per credential **per election**: within an election's factory, a
  nullifier cannot be spent twice; the same credential in a different election yields a
  different (unlinkable) nullifier.
- I3. One voucher per account: `claimVoucher` succeeds at most once per account.
- I4. One voucher per credential (I2 ∘ I3); a citizen can donate at most that one (I1 + no citizen→citizen).
- I5. `citizens.isRegistered` is set only by the factory.
- I6. Only the owner key authorizes an account's actions (forged sig reverts in `validateUserOp`).
- I7. Paymaster sponsors only approved targets.

## 6. Measurement & benchmark requirements

- **B1 Flatness** — donation gas invariant to |citizens| (assert equal at 50 and 5,000).
- **B2 O(1) constants** — claimVoucher / donate / spend(1) / redeem(1).
- **B3 Outflow slope** — spend/redeem gas vs `v ∈ {1,5,10,25,50,100}`; linear fit; `v_max`
  at the 30M L1 block limit.
- **B4 Account creation** — real Groth16 verify + CREATE2 deploy + register.
- **B5 End-to-end** — §4, sponsored, through EntryPoint. Per-step + total.

## 7. Final cost estimate (ultimate deliverable)

Convert measured gas → USD for **L1 and Base**, parameters captured at estimation time:
`ETH_USD`, L1 `gas_price_gwei`, Base `L2_gas_price`, prevailing blob/L1-data fee.

- **L1:** `cost = gas × gas_price_gwei × 1e-9 × ETH_USD`.
- **Base (OP-stack):** `cost = (L2_exec_gas × L2_gas_price + L1_data_fee) × 1e-9 × ETH_USD`,
  where `L1_data_fee` per tx is read from the Base `GasPriceOracle` precompile at
  `0x420000000000000000000000000000000000000F` via `getL1Fee(calldata)` in a Base-forked
  test (`forge test --fork-url <base-rpc>`) or from Base Sepolia receipts.

**Required output:** USD per action (create, claim, donate, spend, redeem) and for the
§8 program totals, under (a) L1 low/normal/high gas and (b) Base at current conditions.

## 8. Program-scale cost model

Per-action gas is O(1) in population. With `d̄` = donations per citizen (≤ 1, one voucher)
and `V = N_cit` vouchers in circulation:

```
total_gas ≈ N_cit  · (a_create + a_claim + d̄·a_donate)   // a_create includes the one Groth16 verify
          + V      · (a_spend_slope + a_redeem_slope)
          + N_cand · (a_register + spend_txs·a_spend_intercept)
          + N_ven  · (a_register + redeem_txs·a_redeem_intercept)
```
Total is linear in population and per-party action counts; the only super-constant
per-transaction cost is a batched outflow, bounded by the block limit (pagination past `v_max`).

## 9. Reproducibility requirement

The deliverable must include a **reproducible test-bench built with Foundry**, with
clear, self-contained setup and run instructions in the project's README, so any
reviewer can rebuild the prototype from a clean checkout and regenerate every
measurement (§6) and the cost estimate (§7). Pin the toolchain and dependencies —
Foundry, solc 0.8.24, OpenZeppelin v5.1, `eth-infinitism/account-abstraction` v0.7, and
circom/circomlib/snarkjs. The instructions themselves belong in that README, not in this
specification. Consider providing a **Dockerfile** that pins the whole toolchain, so the
bench can be rebuilt and re-measured in one command regardless of the host environment.
